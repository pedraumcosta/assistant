Where the gate plugs in: harnesses, models, pipelines

The product ships no agent loop and no model. It attaches to what a team already runs. This page says exactly where: the one attachment point that is binding, the ones that are advisory, what the harnesses give us to work with, which models we call and in what role, and what crosses each boundary. The principle: attach, do not host

Every design topic in the brief has an owner. Most of them are not us, and that is the point. We own the evidence; the team's tools own everything else.

LayerOwnerWhat we touch
The model that writes the codeThe assistant's vendor, chosen by the teamNothing. We record which one it was, in every event
Context, repository understanding, the agent loopThe harnessNothing. The verdict needs none of the author's context; it reads the diff and the contract
Tool permissions, sandbox, budgets across agentsThe team's environment, or an open-source policy planeNothing. A hook of ours may warn; it never blocks
OrchestrationThe build pipelineOne job with fixed steps and one exit status
The contract and the hidden checksOurs, stored on the team's protected branchWritten by the team's first process, pinned by hash
The verdict, the record, the measurementOursThe whole product

Three attachment points follow, and they are not equal. The pipeline's verdict is the one that counts, because it runs where the author cannot reach. A hook inside the harness runs where the author can reach, so it can only ever give early feedback or pause for a person. A meta-harness evaluator sits between the two. I keep the order strict, because the research is explicit that prompt text is "a behavioral wish, not a mechanism", and a hook is a wish with a shell.

The drawing

Attachment point 1: the pipeline, where the verdict binds

This is the shape the prototype already has. The gate runs as a command, reads a base, a head and a contract, and exits 0, 1 or 2. Everything below is what changes between that command and a job in a design partner's pipeline.

The anchor is branch protection, not the pipeline file

Pipeline configuration is author-writable in the ordinary case, so a hash pinned in a workflow protects nothing. The verdict is named as a required status check in the host's branch protection, workflow paths are admin-restricted, and only admins can change the protection rules themselves. This was finding 2 of my design review.

The protected branch is writable by a role no agent assumes

Agents run with the engineer's credentials. If the engineer can push to the contracts branch, so can their agent. The release role that writes there is one nobody delegates to a harness.

Base and head come from the host

In the prototype the base is a fixture copy and the head is a snapshot. In a pipeline the base is the merge-base commit and the head is the PR head, both fetched read-only. The job holds no deployment credentials.

The team's image, the team's test command

The prototype uses one Python image and pytest with a JUnit report. In a pipeline each check is the team's own command in the team's own image, and the pass rule stays the same: exit clean, report readable, exactly the expected count, nothing skipped.

Per-check containers, verdict outside

Running the team's tests means executing the author's code. It runs in a throwaway container per check; the hidden checks are mounted for that one check; the verdict is assembled from exit codes and reports the sandboxed code cannot write. Test infrastructure such as conftest.py is a protected path by default.

Flaky tests get a policy, not a shrug

Checks the team marks retryable get a bounded retry; a check that flips lands in a quarantine state that routes to a person rather than silently passing or failing; flakiness is reported as its own number. Without this the false-fail rate inflates and the gate gets bypassed.

What the pipeline gives back is small on purpose: one status on the PR, the first reason, and a link to the evidence. A visible-check failure is reported in full. A hidden-check failure is reported as the fact of one. The job writes the outcome record and the event log to the customer's own store, where the measurement runner reads them.

# the prototype's command, which is already the shape of the job
python -m prototype.gate.verdict --task <contract id> --base <merge-base> --head <pr head> --out <artifacts>
# exit 0 passed · 1 failed · 2 error (never a pass) → the required status check

What the skill carries, and what it cannot do

The contract reaches the agent as text through a skill file, the same way the prototype's gated arm got its notice. This is what the prototype literally sends, and it is what a skill would say:

This task has a contract, fixed before you started. You cannot change it.
- You may change only: invoicing/pricing.py, tests/**.
- Existing tests and checks may be added to, never removed or altered.
- After you stop, checks you cannot see are run on your change, outside your reach.
  The change is accepted only if they pass.

A skill tells the agent the rules. It enforces nothing, and the study says so in as many words. Enforcement sits in the pipeline and, where the harness has one, in its own policy layer. The prototype has a one-line proof of this split: the gated arm's prompt is text, and the gate's verdict is a separate process that never reads that text.

MCP, if at all

Skills have overtaken MCP as the most adopted extension standard in the corpus. Where a team wants MCP, the server exposes two read-only tools, read the contract and run the visible checks, and no write tool. There is no tool that writes to the protected branch, because there is no legitimate caller for it inside a session.

Attachment point 3: a meta-harness as a channel

Omnigent, the open-source layer from Databricks, wraps 23 harness adapters behind one API and runs a policy plane whose evaluators can be Python, enforced on each vendor's harness through that vendor's own hooks, fail-closed. A gate shipped as one Python evaluator reaches every harness it wraps.

That is one integration in place of nine, so it is worth building third, after the pipeline job and one native hook. Two things keep it third rather than first. It is still inside the author's session, so what it enforces is the early-feedback half, and the binding verdict stays in the pipeline. And it is the most likely competitor to the gate as well as a channel for it: the layer already has policy phases, evaluators, review comments and a conformance bench, and the vendor could add an acceptance gate quickly. I have no adoption data for it. We ship to it because the cost is low, not because it is the strategy.

Models: three roles, none of them the author

The model that writes the code is the team's business. We call a model in three places, each behind an interface, each pinned, each recorded.

RoleWhenConditionsIn the prototype
The author's modelAlways, and never oursAny vendor, through the team's harness and the team's key. Model and version are written on every event and in the outcome record's author field, because results are reported per model and harness pairingClaude Sonnet 5.5 through the published scaffold; the adapter exists only because the scaffold could not call a real API as published
The scorerThe evaluation path only, for software whose behaviour comes from a modelCode scores first: exact match, schema, a required tool call, a tolerance. A model scores only what code cannot. Pinned to a version and a prompt; from a different vendor than the author where possible; checked against human-labelled cases with its agreement stated; reaches only the endpoint the customer configured. A self-hostable classifier is the default; a hosted decision model is an option the customer chooses, and it never gives the correctness verdictDesigned, not built
The comparison evaluatorMeasurement onlyAn evaluator agent from the other vendor, on a sample of runs, so a model family is not grading itself. Its price is recorded as an evidence row before the first callPlanned as a GPT-5.4 model; the adapter was never written

The provider adapter in the prototype is 105 lines because it has to translate the scaffold's message format and supply tool schemas. In the product there is no loop of ours to adapt, so what survives of it is the budget guard: refuse a call whose worst case could pass the contract's verification budget, and compute cost from the provider's token counts and a recorded price.

The reason to re-measure per model and harness pairing is not caution for its own sake. A check that earned its keep on one model was "unnecessary overhead" on the next, in the vendor's own account, and the ablation study found harness components change results in size and sign by model. A model upgrade is a release of the evidence layer too: the measurement runner re-runs, the false-pass rate is compared with the previous one, and the risk tiers move only on the numbers.

The data boundary: what crosses each line

The product works on the customer's code, checks and outcomes, which is what makes it useful and what makes it sensitive. So every artifact has a home, a writer and a reader, and nothing leaves the customer's environment.

Running in the customer's pipeline with the customer's model access and sending nothing back is what makes most procurement questions short. Zero-retention and residency do not apply to us because we hold nothing; single sign-on, model allow-lists and spend controls reduce to honouring what the customer already has. The audit record applies in full, because it is the product.

What I would build first, on one design partner's repository

  1. The pipeline job and the protected branch.

    Reuse their pipeline and their image. Name the verdict as a required check. Create the release role. Port the gate's command to their test runner. This is the binding half, and it needs nothing from any harness vendor.

  2. One native hook, in the harness they actually use.

    A Stop hook that runs the visible checks and returns the first reason, packaged so that Codex and OpenHands load it too. The contract notice becomes the skill file. This is the half that makes the gate pleasant rather than merely strict.

  3. The measurement runner on their history.

    Planted flaws written for their repository, known-good changes from their merged history, the first false-pass and false-fail numbers per model and harness they use. The review notes that retrofitting contracts onto historical changes biases this; I say so in the report rather than hide it.

  4. The meta-harness evaluator.

    One Python evaluator for the policy plane, if the partner runs it. Cheap, and it is a channel, not a dependency.

  5. The scorer interface, when a partner has an LLM application to gate.

    Code scoring first, a pinned model behind the interface, agreement with human labels measured before the first verdict depends on it.

What can go wrong with the integration itself

  • Hook surfaces decay in weeks. The study says the half-life of a distinctive feature is measurable in weeks, and hook inventories are the kind of claim that decays with it. The per-vendor conditional cost is real. That is why the binding attachment is the pipeline, which has no vendor.
  • The vendor ships it natively. A verify-on-stop guard and a goal judge are small features. Our claim rests on independence, a measured error rate and the record, none of which a vendor's own evaluator provides. If buyers do not value those three, there is no product, and the pilot will say so.
  • A real test suite dominates every timing. The prototype's verdict took ten seconds because its tests take under one. A partner's suite sets the latency, which is why checks are applied by risk tier and why the cheap, decisive ones run first.
  • Scope by path is brittle. Lockfiles, formatters and generated code will trip it and inflate false fails. The contract gets declared exceptions, and the false-fail rate is reported beside the false-pass rate so this cannot hide.
  • The pipeline gets edited around. Covered above, and it is the first thing I would verify on a partner's host: that the protection rules themselves are admin-only and that the release role is held by nobody who runs an agent.

The attachment rules are the system design's section 3 and its review's findings 1 to 3; the hook inventory is from the source-code study of eleven harnesses as recorded in the research notes; the model conditions are the design's section 4.2 and decisions ADR-012 and ADR-021. The prototype implements the pipeline shape only; no hook, skill, MCP server or meta-harness evaluator exists in the tree, and this page says so wherever it matters.
