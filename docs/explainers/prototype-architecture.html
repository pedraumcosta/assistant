The scaffold: what it is and why it is someone else's

The agent under test is Listing 3 of the harness study, "a minimum viable harness", reproduced under its CC BY 4.0 licence without a single edit. A test compares the file byte for byte with the recorded listing. If it changed, the test fails.

It is 82 lines, and this is all of it in prose:

  • A Model protocol. One async method, complete(messages, tools) → dict, returning content, tool calls and a cost. Anything that speaks it can drive the loop. This is the seam the whole prototype hangs on.
  • Four tools. bash via subprocess.run(shell=True), read_file, write_file, search_replace. Output truncated at 25,000 characters. Each tool is a plain function in a module-level dict called TOOLS.
  • Context discovery. Reads AGENTS.md from the working directory and every parent, root to leaf, into the system prompt.
  • An Agent dataclass. Messages, turn count, cost, max_turns 50, max_cost 5.00, compaction at an estimated 120,000 tokens that asks the model for a summary and keeps the last 30 percent of turns.
  • The loop. Check limits, maybe compact, call the model, append the response, and if it made tool calls run them one at a time and append each result; otherwise return the content. A tool that raises becomes the string ERROR: Type: message for the model to read.

It is not the product and it was never going to be. It is a citable, neutral author that nobody can accuse me of tuning to suit my gate, small enough that a reader can hold the whole thing in their head while judging the gate around it.

Four things it cannot do as published

I recorded these with the listing rather than fix them in it.

  • Its tool schemas carry a name only, so no real API will accept them.
  • Its limits are signalled with StopIteration inside a coroutine, which Python converts into a RuntimeError. Confirmed on 3.12.9.
  • It runs shell commands on the host with no restriction at all.
  • It reads AGENTS.md from every parent directory of wherever it happens to run, which on my laptop is my home directory.

The scaffold does not know it is in a container. The containers: one image, three jobs

The Dockerfile is six lines: python:3.12-slim plus one pinned pytest. The same image serves three purposes, and the difference is entirely in what is mounted and for how long.

The agent's container

Started once per run with sleep infinity and killed in a finally. Mounts: the run's work/ read-write at /work, the scaffold directory read-only at /opt/scaffold. Each tool call is one docker exec with a 150-second timeout. No network, all capabilities dropped, no new privileges, 256 processes, one gigabyte.

A verdict container per check

docker run --rm with the snapshot read-only at /work, the check files read-only at /checks, an output directory read-write at /out, and a tmpfs at /tmp. The build check additionally mounts gate/tools and first proves the container sees the exact tree the host hashed. Each container exists for one check and is discarded; the hidden checks are co-resident with the author's code only for the seconds that one check takes.

Two ground-truth containers

The same run_once shape, with the acceptance suite and then the base's own tests mounted at /checks. They run after the verdict and the verdict never learns their result.

What a container gives back is deliberately thin: an exit code, stdout and stderr tails, and a JUnit file with a fresh name under /out. The host waits up to three seconds for that file to appear, because Docker's file sharing on this machine can show it a moment late, and a report that never appears is an error, never a pass.

One tool call, traced through all of it

The model decides to run cd /work && cat invoicing/pricing.py. This is what happens, in order, with the file that does it.

  1. The loop calls the model.

    Agent.run() calls model.complete(messages, tool_schemas). The model is a LoggedModel around an AnthropicModel.

    scaffold/listing.py · runner/agent.py
  2. The adapter translates and guards.

    to_api() turns the flat history into system plus messages. The worst-case cost of the call is estimated; if spent plus worst case exceeds the budget, BudgetStop is raised and no call is made. Otherwise the Messages API is called with all four tool schemas declared.

    scaffold/adapter_anthropic.py
  3. The response is logged and returned in the listing's shape.

    Text, tool calls, cost from token counts, usage, and the raw blocks kept under _blocks so they can go back to the model unchanged next turn. LoggedModel writes a model_response event.

    runner/agent.py · runner/events.py
  4. The loop runs the tool call.

    TOOLS["bash"](cmd=...). The listing thinks it is calling its own function. It is calling the proxy.

    scaffold/listing.py line 80
  5. The proxy ships it to the container.

    A tool_call event is written. Then docker exec -i -w /work ‹container› python /opt/scaffold/tool_entry.py with {"op":"tool","name":"bash","args":{"cmd":"..."}} on stdin.

    runner/agent.py · runner/sandbox.py · AgentBox.call()
  6. Inside the container, the published function runs.

    tool_entry.py imports the listing from /opt/scaffold and calls listing.TOOLS["bash"](cmd=...), which is the unedited subprocess.run(shell=True), now with no network and only /work in sight. The reply is {"ok": true, "out": "exit=0\nstdout:..."}.

    scaffold/tool_entry.py · scaffold/listing.py line 13
  7. The proxy logs and returns.

    A tool_result event with duration and the first 4,000 characters. The string goes back into the loop, which appends it as a tool message and calls the model again.

    runner/agent.py

Had the container died in step 5, the proxy raises ContainerFailed, a BaseException, so the listing's except Exception cannot swallow it into a tool result. The run ends with stop_reason: container_error, the ledger is settled, and the outcome's status is error.

The seams, and what they would become

Three places in this architecture are stand-ins for something the product would do differently. Naming them is the honest end of the page.

  • The Model protocol stands in for the team's harness. In the product there is no loop of ours. The adapter shrinks to a scorer client for the evaluation path, and the budget guard survives.
  • The protected/ directory stands in for a protected branch. Here it is unmounted; there it is unwritable by any role an agent assumes, and fetched by hash in a pipeline job.
  • The host process stands in for the pipeline. run.py is what a CI job does: fetch, run checks in containers, assemble a verdict outside them, write a record, exit with one status. The gate already has that command-line form.

One thing the drawing shows that I would change first: the author's code and pytest share a process inside each verdict container, and three of the gate's static checks still sit after the executing ones in the ladder. Neither affected a result on the day. Both are on the list.
